Why GasGuard

ตัวเลขจากเซนเซอร์
ไม่ได้เล่าเรื่องทั้งหมด

การเข้าใจสถานการณ์ LPG ไม่ได้ขึ้นอยู่กับค่าปัจจุบันเพียงอย่างเดียว แต่ยังต้องดูว่าค่ากำลังเปลี่ยนอย่างไร แตกต่างจากภาวะปกติหรือไม่ และเกิดเหตุการณ์อะไรขึ้นในช่วงเวลาเดียวกัน

GasGuard รวมข้อมูลเหล่านี้ เพื่อช่วยเปลี่ยนค่าจากเซนเซอร์ ให้เป็นภาพสถานการณ์ที่ผู้ใช้เข้าใจได้ง่ายขึ้น

ตัวอย่างข้อความตอบสนองของ Prototype:

ตัวอย่างข้อความระบบ: ค่าอยู่ในเกณฑ์จำลองปกติ ติดตามสถานะต่อเนื่องตามรอบการทำงาน

ข้อชี้แจงสถานะต้นแบบ: การจำลองนี้เป็นแบบกำหนดไว้ล่วงหน้า (Deterministic Prototype Simulation) เพื่อแสดงกรอบความคิดในการประมวลผลข้อมูลหลายมิติ ไม่ใช่การเชื่อมต่อเซนเซอร์ฮาร์ดแวร์จริง ไม่ใช่ค่าจากการวัดที่ผ่านการ Calibrate และไม่ใช่ Certified Safety Controller

HOW IT WORKS

จากข้อมูลเซนเซอร์
สู่สถานะที่เข้าใจได้

GasGuard แยกการรับข้อมูล การตรวจสอบ การวิเคราะห์ และการนำเสนอออกเป็นแต่ละชั้น เพื่อให้ข้อมูลสามารถตรวจสอบย้อนกลับ และพัฒนาแต่ละส่วนได้อย่างเป็นระบบ.

01
STAGE 1 SENSOR / DATA SOURCE

รับข้อมูล

รับข้อมูลจากอุปกรณ์หรือแหล่งข้อมูลจำลอง เช่น บอร์ด ESP32, โครงสร้างเซนเซอร์ MQ-3 / MQ-6 หรือข้อมูลจำลองในระบบ

รายละเอียดทางเทคนิค
  • รองรับ HTTP Ingress & โครงสร้าง MQTT Protocol
  • แยกสัญญาณดิบ Raw ADC reading ออกจากชั้นประมวลผล
  • โหมดการจำลอง Deterministic Simulation ภายในเบราว์เซอร์
ข้อชี้แจงต้นแบบ: อยู่ระหว่างเตรียมการทดสอบกับฮาร์ดแวร์จริง ยังไม่มีการ Calibrate ทางกายภาพ
→
02
STAGE 2 MEASUREMENT

ตรวจและเตรียมข้อมูล

ตรวจโครงสร้างข้อมูลดิบ และเตรียมข้อมูลก่อนส่งเข้าสู่ Telemetry โดยแยกกระบวนการตรวจสอบออกจากเซนเซอร์

รายละเอียดทางเทคนิค
  • ตรวจสอบโครงสร้าง Raw Payload Schema Validation
  • Sensor Adapter Boundary รองรับ Voltage และสัญญาณดิบ
  • เตรียมความพร้อมสำหรับกระบวนการแปลงหน่วย ppm
ข้อชี้แจงต้นแบบ: ยังไม่แปลงค่าดิบเป็น ppm แท้จริงจนกว่าจะผ่านการ Calibrate ทางกายภาพ
→
03
STAGE 3 TELEMETRY

จัดรูปแบบข้อมูลกลาง

สร้างข้อมูลตาม Telemetry V1.1 พร้อม identity, boot/session sequence และข้อมูลเวลาที่ระบบต้องใช้

รายละเอียดทางเทคนิค
  • มาตรฐานข้อมูลกลาง Telemetry V1.1 กำกับด้วย Device Identity
  • กำกับเซสชันด้วย bootId และ sequence แบบ monotonic
  • ระบบป้องกันข้อมูลค้าง (Stale), ซ้ำ (Duplicate) หรือสลับลำดับ (Out-of-order)
→
04
STAGE 4 SAFETY ANALYSIS

วิเคราะห์สถานการณ์

ใช้ข้อมูลปัจจุบัน แนวโน้ม baseline และ prototype rule set เพื่อสร้างสถานะสำหรับ UI

รายละเอียดทางเทคนิค
  • คำนวณอัตราการเปลี่ยนแปลง Rate of Rise (ppm/min)
  • เปรียบเทียบแนวโน้มกับ Dynamic Baseline และ Variance
  • ประเมินระดับความปลอดภัยด้วย Safety Rule Engine v0.1 (Rule-based)
ข้อชี้แจงต้นแบบ: ประเมินตามกฎต้นแบบ ไม่ใช่การวินิจฉัยก๊าซรั่วสมบูรณ์แบบหรือมาตรฐานรับรองความปลอดภัย

STAGE 5 EXPERIENCE

แจ้งเตือนและแสดงผล

นำผลไปแสดงใน Dashboard, Alerts, Events และ workflow ตามบทบาทผู้ใช้

รายละเอียดทางเทคนิค
  • แยกพื้นที่ทำงานตาม 4 บทบาท (General, Technician, Admin, Developer)
  • บันทึก Timeline เหตุการณ์เพื่อการตรวจสอบย้อนหลัง (Audit Trail)

BUILT FOR EVERY ROLE

แต่ละคนเห็นสิ่งที่จำเป็น
ต่อหน้าที่ของตัวเอง

GasGuard แยกมุมมองตามหน้าที่ เพื่อให้ผู้ใช้ทั่วไป ทีมซ่อมบำรุง ผู้ดูแลระบบ และทีมพัฒนา ไม่ต้องรับข้อมูลที่ซับซ้อนเกินความจำเป็น.

GENERAL ผู้ใช้งานทั่วไป
“ตอนนี้พื้นที่ของฉันเป็นอย่างไร?”

ผู้ใช้ต้องการทราบสถานะความปลอดภัยในพื้นที่ของตนอย่างรวดเร็ว ได้รับการแจ้งเตือนที่เข้าใจง่าย และมีขั้นตอนที่ชัดเจนเมื่อเกิดเหตุ โดยไม่ต้องมีความรู้ด้านเทคนิคเซนเซอร์

สิ่งที่ต้องการและโฟกัสหลัก:

  • ภาพรวมความปลอดภัย: ดูสถานะรวมของพื้นที่ (ปกติ / เฝ้าระวัง / ความเสี่ยงสูง)
  • การแจ้งเตือนและเหตุการณ์: รับข้อความแจ้งเตือนที่เข้าใจได้ทันที ไม่สับสน
  • คำอธิบายสถานการณ์: ทราบเหตุผลเบื้องต้นของสถานะโดยไม่ต้องอ่านข้อมูล telemetry ดิบ
  • การจัดการพื้นที่: ระบุตำแหน่ง เช่น ครัวร้านอาหาร หรือพื้นที่ถังแก๊สอย่างชัดเจน

  • ลำดับขั้นตอนบริการ (Service Workflow): ตรวจสอบการติดตั้งและบันทึกผลการทดสอบ

ออกแบบโครงสร้างรองรับเซ็นเซอร์ก๊าซและแอลกอฮอล์ โดยแยกกระบวนการ Calibration ออกจาก Raw Reading

Measurement Layer

ตรวจสอบความถูกต้องของ payload ดิบก่อนเข้าสู่ระบบ ป้องกันข้อมูลผิดพลาดที่อาจกระทบต่อ Engine

Telemetry V1.1 Standard

มาตรฐานข้อมูลกลาง กำกับ session ด้วย bootId และ sequence แบบ monotonic เพื่อความแม่นยำ

Data Protection Engine

ตรวจจับและปฏิเสธข้อมูลค้าง (Stale), ข้อมูลซ้ำ (Duplicate) และข้อมูลที่มาสลับลำดับ (Out-of-order)

Explainable Safety Scoring

คำนวณคะแนนความปลอดภัยและระดับความเสี่ยง (0-100) พร้อมเหตุผลประกอบที่ตรวจสอบย้อนกลับได้

Multi-Source Pipeline

รองรับทั้งการจำลองในเบราว์เซอร์ (Simulation), การเชื่อมต่อผ่าน REST API และ MQTT Protocol

Strict Workspace Isolation

แยกพื้นที่จำลอง (Demo Site), พื้นที่ทดสอบ (Device Test) และฮาร์ดแวร์จริง (Hardware Pilot) ไม่ปะปนกัน

    ค่าพื้นฐาน

    LPG reading
    ค่าความเข้มข้น LPG ที่ผ่าน data contract แล้ว แสดงเป็น ppm ใน prototype นี้
    Raw value
    ค่าจาก sensor ก่อนการปรับ calibration ใช้สำหรับ engineer ตรวจสอบ ไม่ควรตีความเป็น ppm โดยตรง
    Temperature / Humidity
    บริบทแวดล้อมที่ใช้ปรับ confidence เพราะ sensor บางชนิดไวต่อสภาพแวดล้อม

    การวิเคราะห์แนวโน้ม

    Baseline
    ค่าเฉลี่ยของ historical readings ที่ใช้เป็นพฤติกรรมคาดหมายของโซนนั้น
    Rate of rise
    ความเร็วที่ LPG เปลี่ยนในช่วงล่าสุด หน่วย ppm/min, ค่าบวกสูงหมายถึงกำลังเพิ่มเร็ว
    Exposure
    ผลรวมส่วนที่สูงกว่า baseline ตามเวลา ช่วยแยก peak สั้นจากระดับสูงสะสม
    Variance
    ความผันผวนของข้อมูลย้อนหลัง ใช้เทียบว่าค่าปัจจุบันต่างจาก noise ปกติมากแค่ไหน

    ความน่าเชื่อถือและสุขภาพ

    Sensor confidence
    คุณภาพของ reading โดยพิจารณา humidity, variance และเงื่อนไข prototype ไม่ใช่ความแม่นยำที่รับรองแล้ว
    Baseline drift
    การเปลี่ยนจากค่าอ้างอิง ใช้เป็นสัญญาณให้วางแผน calibration หรือ inspection
    Sensor health
    ตัวชี้วัด maintenance จาก drift, variance, confidence และ connectivity
    Unknown
    sensor/connection ไม่พร้อม จึงไม่สร้าง risk score และห้ามอ่านว่า safe

    การตัดสินใจ

    Anomaly score
    ความต่างจาก pattern ปกติ โดยอาศัย deviation, rate และ valve context
    Risk score
    ผล rule-based ที่รวม LPG, rate, exposure, anomaly, valve และ confidence เพื่อจัดลำดับความสำคัญ
    Safety state
    safe, attention, critical หรือ unknown เป็นข้อความสรุปที่ต้องดูเหตุผลใน Safety Intelligence ประกอบ
    Event classification
    คำอธิบาย pattern เช่น expected operation, abnormal rise หรือ monitoring unavailable

    What is GasGuard?
    GasGuard คือแพลตฟอร์มสำหรับติดตาม วิเคราะห์ และช่วยจัดการข้อมูลความปลอดภัย LPG เพื่อให้ผู้ใช้เห็นสถานะล่าสุด เหตุการณ์ที่ควรติดตาม และประวัติการดำเนินงานในที่เดียว
    ขอบเขตปัจจุบันSafety Engine เป็น prototype สำหรับพัฒนาและทดสอบ ยังไม่ใช่ certified safety controller และไม่แทนอุปกรณ์ป้องกันที่ผ่านการรับรอง

    Technology
    • ESP32 readinessเตรียม contract สำหรับเชื่อมอุปกรณ์จริง
    • MQ-3 / MQ-6 architectureแยก adapter ตามชนิด sensor โดยยังไม่อ้างว่า calibration เสร็จแล้ว
    • Measurement Layerตรวจข้อมูล raw ก่อนเข้าสู่ระบบ
    • Telemetry V1.1รูปแบบข้อมูลกลาง พร้อม boot session และเวลา receive
    • Data protectionตรวจ stale, duplicate และ out-of-order
    • Safety Engineสรุป safety และ risk state จากข้อมูลที่รับได้
    • Data sourcesรองรับ Simulation และเตรียมขอบเขต REST / MQTT
    • Role-based accessแยกหน้าที่ General, Technician, Admin และ Developer
    
          
    Safety Intelligence
    ระบบพิจารณาค่าก๊าซ แนวโน้ม ความต่อเนื่อง และคุณภาพข้อมูล เพื่อสร้าง safety state และ risk สำหรับช่วยให้ผู้ใช้ติดตามสถานการณ์
    Prototype limitationผลวิเคราะห์ต้องผ่านการตรวจสอบกับ sensor, สภาพแวดล้อม และข้อกำหนดด้านความปลอดภัยจริงก่อนนำไปใช้งานภาคสนาม
